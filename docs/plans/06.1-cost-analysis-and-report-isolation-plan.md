# Step 6.1: Cost analysis and report isolation

## Summary

This step finds the other places where a large cost can hide in a repository, and it keeps the report work separate from the database build.

- At this time, `init` always runs the analysis passes (`analyze` in `src/commands/init.rs`) and prints the analysis section. The analysis shows the largest blobs and trees, the commits that add the most blob data, the paths with the most blob versions, and the directories with the most data on disk (trees of the directory plus the blobs directly in it).
- After this step:
  - The analysis passes are in `src/report.rs`. `init` runs them only with `--report`. A database build (step 7) does not run them.
  - The report also shows directory totals that include all subdirectories, the cost that each ref namespace keeps alive, the cost that one ref keeps alone, the storage overhead of the packs, and the ref count of each namespace.
  - The reachability walk also calculates which refs keep each object. This is data for the database, not a report pass.
  - Plans 07 and 08 show where each value goes in the database, and which report is a SQL query.

## Where a large cost can hide

| Area | How it gets large | Status before this step |
|---|---|---|
| Blobs | Large files, files with many versions | Shown |
| Trees of one directory | A wide directory that changes frequently | Shown (direct only) |
| A directory with all subdirectories | A vendored or generated directory with many small unique files | Not shown |
| Refs of one namespace | Tags or remote-tracking refs that keep history that no branch has | Not shown. Liveness tells only "a ref keeps it" |
| One ref | One old tag or branch that alone keeps a large history | Not shown |
| Ref count | Many refs make each fetch advertise more refs. Not a disk cost | Total only |
| Commit and tag objects | Many bot commits, long messages | Not shown |
| Storage overhead | The same object in two packs, loose copies of packed objects, large objects stored without a delta | Not shown. The data is in `ObjectCopy` |
| Reflogs and unreachable objects | Old history after a rewrite | Shown (`ReflogOnly`, `Unreachable`) |

## Where each check goes, and its cost

"Report" means a pass in `src/report.rs` that runs only with `init --report`. "Build" means work that `init` does for the database, also without `--report`. The costs are estimates. Measure each one (see "Make sure the result is correct").

| Check | Where | Folded into | Estimated cost (linux / 1JS) | In the database (steps 7 and 8) |
|---|---|---|---|---|
| Directory totals with all subdirectories | Report | The directory pass. After the direct sums, one loop over the path ids from high to low adds each path to its parent. A parent path is a prefix of its child, so its id is smaller (step 6 sorts the ids by bytes) | < 5 ms | Query. The `paths.full_path` range `[dir/, dir0)` selects a subtree, because `0` is the byte after `/`. No new column |
| Kept by one ref namespace | Build | The reachability walk (see "Kept-by state") | +0.2 to +0.6 s for both kept-by values together | New columns `kept_by_kind` on `commits`, `trees`, `blobs`, `tags` |
| Kept by one ref | Build | The same walk, the same state word | Included above | New columns `kept_by_ref_id` (NULL if more than one ref keeps it) |
| Ref count of each namespace | Report | None. One loop over `container.refs` | < 1 ms | Query on `refs.kind` |
| Commit and tag object totals | Report | The `all_disk` sums of the directory section. They already add each type | 0 | Query on `commits`, `tags` |
| Storage overhead | Report | Its own pass over `container.copies`. The copies are not grouped by path, so this does not fold into the directory pass | 10–30 ms | Query on `object_copies`. Step 8, report 5, already plans this |

Only the kept-by values are build work, because the database needs them and SQL cannot calculate them: a walk of the full graph in SQL needs the tree edge tables, and step 7 does not write them by default. All other checks are report passes in memory, or SQL queries on the database.

## Kept-by state

The reachability walk now keeps one `AtomicU8` liveness for each object, and moves it up with `fetch_max`. This step replaces it with one `AtomicU64` state word for each object:

- Bits 0–7: the liveness, as now. Merge with `max`.
- Bits 8–15: the kept-by kind: none, one kind (`Branch`, `Remote`, `Tag`, `Stash`, `Head`, `Other`, index, reflog), or more than one kind. Merge: none + X = X, X + X = X, X + Y = more than one.
- Bits 16–47: the kept-by ref: none, one ref index, or more than one ref. The same merge.

Each merge is commutative and associative, so the result does not depend on the thread count or the sequence. A value can change at most two times (none, one, more than one), and the liveness at most three times. Thus each object is visited a small number of times, not one time for each ref.

- Commits: the scan in falling rank order stays. It merges states as it now takes the `max`.
- Trees and blobs: a level walk from all roots. A thread reads the state first and does a `compare_exchange` loop only when the merge changes the value. It pushes the child only when the value changed. Most shared children reach "more than one" early, then each visit is one read.
- A symbolic `HEAD` is not a separate ref. Only a detached `HEAD` (`RefKind::Head`) counts.
- Memory: 8 bytes for each object (84 MB on linux, 74 MB on 1JS), in place of 1 byte. The peak heap is in the parse (9.1 GB on linux), so the peak does not change.

The walk now stops at an object that has a liveness at least as strong as the new one (strongest state first). With the kept-by values, the walk can stop only when no value changes. Thus it does more visits. The estimate above is from 2 to 3 visits for each object in place of 1. Measure it.

## Decisions needed before this step

Ask the user to select one option for each decision. Record the decisions in the step report.

1. **The in-memory report after step 8.**
   1. **Recommended:** keep `init --report`. It gives the reports without a database file, in less than 0.1 s more than the parse. `analyze` (step 8) gives the same reports from the database with SQL.
   2. Remove the in-memory report in step 8. Then there is only one copy of each report, in SQL.
2. **Kept-by detail.**
   1. **Recommended:** the kind and the single ref, in the same walk.
   2. The kind only. Less memory (2 bytes for each object), and slightly fewer visits.
3. **Kept-by cost.**
   1. **Recommended:** always calculate it if the measured extra time on 1JS is 0.5 s or less. If it is more, calculate it only with `--kept-by`.
   2. Always calculate it.
   3. Only with `--kept-by`.
4. **Directory totals in the database.**
   1. **Recommended:** a SQL query in step 8 (`GROUP BY introduced_at_path_id`, then the subtree range of `full_path`). Measure it on the 1JS database. If it takes more than 2 s, add a `path_stats` table that the write fills from the in-memory sums.
   2. Always write a `path_stats` table. This adds approximately 0.3 s to the build (an estimate: 0.53 M rows).
