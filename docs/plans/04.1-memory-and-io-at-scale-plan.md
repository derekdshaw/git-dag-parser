# Step 4.1: Memory and I/O at scale

## Summary

This step makes the parser work on very large repositories.

The parser reads a repository in two passes. Before step 4.1, pass 2 used too much memory on large repositories:

- The parser kept each tree entry as a 64-byte struct, plus a heap allocation for its name. With the maps and edge lists around them, this cost about 140 bytes for each tree entry.
- The linux repository has about 528 million tree entries. The parser passed 48 GB of heap during pass 2 and did not complete.
- git-ms has about 147 million tree entries. The heap grew from 0.3 GB after pass 1 to 17.6 GB after pass 2.

Parts 1, 2, 3a, 3b, 4, and 5 are done. After part 2, linux completes with a 15.88 GB peak heap and git-ms peaks at 3.27 GB (see "Current measurements"). After part 3b, with `mimalloc` as the allocator of the binary, linux takes 132.5 s with a 9.01 GB peak heap, and git-ms takes 21.0 s with a 2.72 GB peak heap (see "3b. Validation"). All goals of this step are met. Part 4 makes pass 2 use 5–23% fewer instructions (see "4. Decompression in pass 2"). Part 5 makes pass 2 parallel: on 32 threads, linux parses in 24.5 s with a 9.18 GB peak heap, and git-ms in 3.65 s with a 2.09 GB peak heap (see "5. Parallel pass 2"). Pass 1 is now most of the time (18 s of 24.5 s on linux), and it is as fast as `git cat-file`. Part 6 is next: a parallel header scan inside one pack, after a new profile and a design that the user approves (see "6. Pass 1").

Pass 2 also does unnecessary work. Parts 3 to 5 fix this:

- The delta cache keeps each base that it builds and never removes one (1.8 GB for one pack of git-ms). It does not keep an object that pass 2 reads, so a base that pass 2 also reads is inflated two times. Fixed in part 3.
- Each cache hit copies the cached bytes. Fixed in part 3b.
- Each object gets a new zlib decoder, and its output buffer grows from zero. Fixed in part 4.
- Pass 2 uses one thread on a machine with 128 cores. Fixed in part 5.

After this step:

- Tree entries are in compact arrays of about 9 bytes for each entry (done in part 2).
- A name store keeps each distinct entry name one time. Each entry refers to its name by a 4-byte id (done in part 1).
- Pass 1 records the base of each delta. The delta cache keeps a base only until its last request. It has a byte limit for safety, and it returns references, not copies (done in parts 3a and 3b).
- Pass 2 reuses its decoders, allocates each output one time (done in part 4), and uses many threads (done in part 5).

Step 5 cannot run on large repositories without this step. Step 5 keeps all tree entries in memory for its calculation.

## Current state of the code

### How `parse_objects` works

`parse_objects(git_dir)` in `src/parser/mod.rs` does this:

1. **Pass 1** (`src/parser/scan.rs`, `scan_repository`):
   - It reads the pack indexes and the loose object names.
   - It reads each pack's object headers in pack-offset order (`scan_pack` in `src/parser/pack.rs`). It inflates only the first bytes of each delta, to get its result size. One reused `flate2::Decompress` reads all deltas of a pack.
   - `scan_pack` also returns a `DeltaGraph`: the position of the base of each delta in the pack (part 3a). After pass 1, `simulate_cache` logs the simulated delta cache peak of each pack.
   - It records every copy of every object in `container.copies` and selects a primary copy for each object.
   - `Scan::finish` sorts each object kind by hash. An object's index is its position in hash order.
   - `scan_pack` collects all entries of a pack in a `Vec<ScannedEntry>` before `Scan::record` gets them.
2. **Pass 2** (`src/parser/bodies.rs`, `read_bodies`):
   - It reads commits, trees, and tags from their primary copies, in pack-offset order. It never inflates blobs.
   - `PackReader::read` (`src/parser/pack.rs`) inflates each object with `inflate`. Each reader has one `Decompress`, reset for each object. The output is allocated one time with the size from the entry header: the object size, or the delta data size for a delta (part 4).
   - `PackReader` reads by position in the pack. Before it reads a pack, it gets the time of each request from the `DeltaGraph` (`request_times`). The `DeltaCache` (`src/parser/delta_cache.rs`) keeps each base until its last request, and a hit returns a reference. When the cache is full, rule B evicts the entries that are needed farthest away (part 3b). The byte limit is 1 GiB (`init --delta-cache-size`).
   - It parses each commit body into `commits_raw: HashMap<ObjectHash, CommitRaw>`.
   - `parse_tree` (`src/parser/content.rs`) interns each entry name in one `NameStore`, resolves each entry hash to a child index through the `HashIndex`, and records the entry in a `TreeEntriesBuilder`. It does not keep the entry hash.
   - It writes the name and target hash of each tag into `container.tags[i]`.
   - `TreeEntriesBuilder::finish` copies the entries into tree index order. `read_bodies` returns `Bodies { commits_raw, tree_entries, names }`.
3. **After pass 2**: `resolve_commits`, `resolve_tags`, and the ref reader resolve hashes to indices.

`parse_objects` returns the tuple `ParsedObjects = (commits_raw, tree_entries, names, hash_index, container)`. `parse_objects_with(git_dir, &ParseOptions)` also sets the delta cache limit.

`init` (`src/commands/init.rs`) runs only `parse_objects` and prints the summary. Part 2 removed `build_relationships` (`src/parser/relationships.rs`, the "Phase 2" of `init`). Step 5 adds its replacement.

### Data structures

- `src/models/name_store.rs`:
  - `NameStore` holds an `intaglio::bytes::SymbolTable<ahash::RandomState>` and a running byte total. Methods: `intern`, `get`, `len`, `total_bytes`.
  - `NameId` is a `u32` newtype (4 bytes). `intaglio::Symbol` is not used outside this file.
- `src/models/container.rs`:
  - `TreeEntries` has four arrays: `start: Vec<u64>` (one item for each tree, plus a last item that is the entry count), `child: Vec<u32>`, `name: Vec<NameId>`, and `mode: Vec<u8>`. This is about 9 bytes for each entry. `TreeEntries::NO_CHILD` (`u32::MAX`) is the child of a submodule or of a child that is not in the store. Methods: `len`, `entry_count`, `entries(tree)`.
  - `TreeEntriesBuilder` records the entries in the order pass 2 reads them, with a `(first position, count)` span for each tree (`Vec<(u64, u32)>`). `finish` copies each array into tree index order, one array at a time.
  - `FileKind` is `repr(u8)`, one byte.
  - `CommitRaw { index, root_tree_hash, parent_hashes, commit_time }`.
  - `HashIndex` is one `HashMap<ObjectHash, ObjectId>`.
  - `ObjectContainer` has `commits`, `trees`, `blobs`, `tags`, `refs`, `packs`, `copies` (`ObjectCopy`, 32 bytes), and `loose_mtimes`. It does not hold a `NameId`.

  - `Commit` is 96 bytes. `Tree` and `Blob` are 48 bytes each (`index`, `hash`, `size`, `size_disk`).
  - Object indices are `usize`. Only `TreeEntries.child` uses `u32`.

## Words used in this plan

- **Name store**: a string interner for byte strings (names). It keeps each distinct name one time and gives it a small id. You use the id to get a `&[u8]` reference to the bytes.
- **Interning**: if a name is already in the store, return the id that exists. Do not add the name again.
- **Flat entry arrays**: all tree entries of all trees in a small number of large arrays. Each tree has a start position and an end position in these arrays.
- **Offset order**: the order of objects in a pack file, from the start to the end.
- **Peak heap**: the largest `RssAnon` value of the process (`/proc/<pid>/status`). It does not include the mapped pack pages.
- **Position, read, build, request, live entry**: part 3 defines these words.
- **Delta family, work unit, worker, merge**: part 5 uses these words. "Terms" in `README.md` defines them.

## Decisions already made

- Use `intaglio::bytes::SymbolTable` (crate `intaglio` 1.15, feature `bytes` only) with the `ahash` hasher as the name store. Put it behind our own `NameStore` type, so that the rest of the code does not use `intaglio` directly. Do not keep a `Vec<u8>` for each entry name.
  - `lasso` and `string-interner` accept only UTF-8 `str`. Git names are bytes, so these crates do not fit.
  - `intaglio` keeps each distinct name in its own allocation. This is not a problem: linux has about 100,000 distinct names, so the store has about 100,000 allocations (before part 2, the parser made one allocation for each of about 528 million entries).
  - Its symbols are `u32`. linux has 98,271 distinct names, which is more than `u16` can hold.
- Use `u32` for object indices in the stored data. linux has 10.4 million objects. The limit of `u32` is about 4.29 billion.
- Remove `Tree.blobs`, `Tree.subtrees`, and `Blob.trees`. The flat entry arrays replace them. Calculate reverse edges only when a later step needs them.
- Name ids are for internal use only. Do not write them to a database. Do not use them as a sort key or a tie-break. Thread order can change them between runs.
- Use `flate2` with the `zlib-rs` backend. Reset and reuse decoders. Give each worker its own decoder. Do not share a decoder between threads.
- Pass 1 records the base of each delta in a `DeltaGraph`. Pass 2 counts the requests for each entry before it reads a pack, and removes a cached entry at its last request. Do not use an LRU cache crate. Pass 1 gives the full read order of pass 2. The byte limit is only for safety.
- The delta cache evicts the entry with the farthest next request first (rule B, 3b item 6). 3a selected it: the linux pack has a simulated peak of 1206.17 MiB, which is more than 1 GiB. The user approved rule B.
- Give the delta caches one total byte limit for all workers together. Divide the limit between the workers. Do not give each worker a fixed size: 128 workers with 256 MB each would use 32 GB.
- Measure memory as peak heap (`RssAnon`). Do not use `VmRSS`, which includes the mapped pack pages that the system can release.

### 3. Delta cache from the pass 1 delta graph (done, commits `87c88e1` and `da60bf4`)

Do this part in two commits: 3a, then 3b. Get approval for each.

#### The problem

- Pass 2 builds a delta from its base. The base can also be a delta, so pass 2 builds the full chain. `resolve_object_at_offset` (`src/parser/pack.rs`) keeps each base that it builds, and it never removes one. For linux, the cache holds 6.98 GB at the end of the pack.
- `PackReader::read` does not cache the object that it returns. If a later delta uses that object as its base, pass 2 inflates the object again.
- Pass 1 finds the base of each delta (`delta_base` in `scan_pack`), but it does not keep it.

#### The solution

- Pass 1 keeps the base of each delta in a `DeltaGraph`.
- Before pass 2 reads a pack, it counts the requests for each entry of the pack.
- The cache keeps an entry only while it has requests that are not done. It removes the entry at its last request.
- A byte limit is for safety. It is necessary only if the live entries hold too many bytes at one time.
- Do not use an LRU cache crate. An LRU cache predicts the next requests from the last requests. Here, pass 1 gives the full read order of pass 2. Thus the cache knows which entries it needs again.

#### Words used in this part

- **Position**: the index of an entry in the offset order of its pack, from 0 to the entry count minus 1. This is `pos` in `scan_pack`. The entry at position `i` of a pack is the copy `container.copies[first_copy + i]` (see 3a item 3).
- **Read**: pass 2 reads the body of a copy that is packed, primary, and not a blob. The reads of a pack are in position order.
- **Build**: make the bytes of an entry. For an entry that is not a delta, inflate it. For a delta, inflate it and apply it to the bytes of its base.
- **Request**: one use of the bytes of an entry. A read of an entry is one request for that entry. The first build of a delta is one request for its base.
- **Live entry**: an entry that is in the cache.

     ```
     total    = sum of requests                     // before the loop changes them
     state    = vec![NotBuilt; n]
     stack    = Vec::new()
     for p in reads:
         stack.clear()
         c = Some(p)
         while let Some(x) = c:                     // go up the chain to a built entry
             if state[x] != NotBuilt: break
             stack.push(x)
             if stack.len() > MAX_DELTA_DEPTH: return the same error as resolve_object_at_offset
             c = graph.base(x)
         if let Some(x) = c:                        // x is live: one request for it
             debug_assert!(state[x] == Live && requests[x] > 0)
             requests[x] -= 1
             if requests[x] == 0: state[x] = Done; bytes -= size(x); entries -= 1
         while let Some(x) = stack.pop():           // build, deepest base first
             requests[x] -= 1
             if requests[x] > 0:
                 state[x] = Live; bytes += size(x); entries += 1
                 peak_bytes = max(peak_bytes, bytes); peak_entries = max(peak_entries, entries)
             else:
                 state[x] = Done
     ```
     - The stack gives the deepest base first. This is the same order as the 3b algorithm (item 4 of 3b), which builds a base before the delta that uses it. Thus, with no eviction, the 3b peaks are equal to the simulated peaks.

   ```
   // One request for the entry at c
   fn request(c, depth) -> Result<Bytes>:
       if cache has c:
           hits += 1
           requests[c] -= 1
           if requests[c] == 0: return Owned(cache.take(c))   // the last request: no copy
           cache.set_next(c, next(c))
           return Cached(c)
       first = !built[c]
       if !first: misses += 1                    // c was evicted or too large: build it again
       bytes = build(c, first, depth)?
       built[c] = true
       requests[c] -= 1
       return keep(c, bytes)

   // Bytes of c for a second build of a delta. This does not change a count.
   fn fetch(c, depth) -> Result<Bytes>:
       if cache has c: hits += 1; return Cached(c)
       misses += 1
       bytes = build(c, false, depth)?
       return keep(c, bytes)

   fn keep(c, bytes) -> Bytes:
       if requests[c] > 0:
           match cache.insert(c, bytes, next(c)): Ok => Cached(c), Err(bytes) => Owned(bytes)
       else: Owned(bytes)

   // Time of the next request of c. Use it only when requests[c] > 0.
   fn next(c) -> u32:
       times[time_start[c + 1] - requests[c]]

   fn build(c, first, depth) -> Result<Vec<u8>>:
       if depth > MAX_DELTA_DEPTH: error "Delta chain too deep"
       match graph.base(c):
           None    => inflate the entry at c
           Some(b) =>
               delta = inflate the delta payload of the entry at c
               base  = if first { request(b, depth + 1)? } else { fetch(b, depth + 1)? }
               apply_delta(bytes of base, &delta)   // Cached(p): cache.get(p); Owned(v): &v

   fn read(pos) -> Result<&[u8]>:
       match request(pos, 0)?:
           Cached(p) => cache.get(p)
           Owned(v)  => { out = v; &out }
   ```
   - Only the first build of an entry requests its base. A second build uses `fetch`. `count_requests` counts one request for each first build, so the counts stay correct after an eviction.

     ```
     need    = self.bytes + len - limit             // bytes to free
     victims = Vec::new()                           // items (t, p) to evict, farthest first
     freed   = 0
     while freed < need:
         (t, p) = pop items from heap until one is not old    // expect: heap is not empty
         if t <= next:                              // p is needed no later than the new entry
             heap.push((t, p))
             for v in victims: heap.push(v)         // keep all entries
             bypassed += 1
             return Err(bytes)
         victims.push((t, p))
         freed += len() of the entry at p
     for (_, p) in victims:                         // evict
         remove the entry at p; bytes -= its len(); evictions += 1
     ```
     - Do not evict an entry before you know that the new entry will be cached. If `insert` evicts entries and then does not cache the new entry, the evictions are wasted. A loop that evicts while it looks would evict X, then find Y, and then not cache N. The algorithm above finds Y first, keeps X and Y, and does not cache N.
     - For equal times (`t == next`), keep the cached entry.
     - `heap` cannot become empty in the loop. `len <= limit`, so `need <= self.bytes`. If all cached entries are farther than the new entry, the loop frees enough bytes before it pops the last of them. Use `expect` with a message for this.
     - The items in `victims` are not old, so `insert` can push them back to `heap` without a check. Do not make the heap again after these pushes. They do not add items.
     - Cost: O(k log n), with k the number of items that the loop pops.
   - **Keep the heap small.** After the push in `insert` and the push in `set_next`, if `heap.len() > 2 * entries.len()`, make the heap again from `entries`: `BinaryHeap::from(Vec of (next, position) of each entry)`. ### 5. Parallel pass 2 (done, commits `7074a8e`, `5a511c2`, `22ad553`, and `d21af25`)

1. Divide the commits, trees, and tags of each pack into work units of whole delta families (`src/parser/work.rs`). Give the units to the workers. Use `rayon`.
   - Each delta has one base, so the deltas of a pack make a set of trees: the delta families. A unit takes whole families, in the order of their first read, until it has the target number of reads. The reads of a unit are in offset order. No worker needs a base that a different worker built, and no base is built two times.
   - Loose objects are not in a pack. Put their copies in units of their own. A worker reads a loose object with `read_loose_object`.
   - This replaces the first plan: ranges in offset order, cut at read positions where the cache has 0 live entries. Real packs have too few of these positions. With 128 ranges, linux would build 18.2 million bases again for 7.6 million reads, and the largest git-ms pack has 2 such positions. The families are small: the largest linux family has 0.14% of the reads.
2. Let the workers borrow the shared data. Do not use `Arc`, `thread::spawn`, or a channel.
   - `rayon` returns only after all workers are done. Thus the workers can borrow values from `read_bodies`. The values do not have to be `'static`. (`build_relationships` used `Arc` only because `thread::spawn` needs `'static` values.)
   - The workers borrow these values and only read them:
     - the open packs (`&[OpenPack]`: the mapped pack bytes and the pack index),
     - the pass 1 result (`&Scan`: `container.copies`, `container.hash_of`, and `primary`),
     - the hash index (part 2 resolves each entry hash to a child index during the parse),
     - `objects_dir`, for loose objects.
   - All these types are `Sync`. Each worker makes its own `PackReader` from `&OpenPack`. `PackReader::new` borrows the pack bytes and the index. It does not copy them.
   - No worker changes `scan.container` during pass 2. Today pass 2 writes the name and target of each tag into `container.tags[i]`. Instead, each worker returns its tags as records. Write them into the container after all workers are done.
3. Each worker owns its delta cache (a part of the total limit), its decoder, and its `NameStore`. Workers do not share a name store and do not use locks for names.
   - Each worker makes a `PackReader` for its range. The reader calls `count_requests` with the reads of its range only. If a worker needs a base that is in a different range, the worker builds it again. The result is correct, because the workers only read the pack bytes.
   - In part 3, `PackReader` keeps `requests` and `built` in arrays with one item for each position of the pack. Do not do this for each worker: for linux, 128 workers × 10.5 million positions × 5 bytes is about 6.7 GB. Keep them in a `hashbrown::HashMap<u32, (u32, bool)>` (position → requests, built) with only the positions that the range requests.
   - Change `count_requests` for the same reason. In part 3 it makes `requests` and `needed` as arrays with one item for each position of the pack. For a worker, it must return the map, and it must keep `needed` in a map or a set.
4. Each worker returns its trees as local flat arrays (with local name ids), its commits as raw records, and its tags as records.
5. Merge the results in tree index order:
   - Merge the worker name stores into one store. For each worker, make a table from its local ids to the merged ids. The stores are small (about 100,000 names for linux), so the merge is fast.
   - Change each local name id in the worker's entry arrays to the merged id.
   - The merged result must be the same for any number of threads. Merge the workers in a fixed order (their range order). Name ids are for internal use only, but the entries must be equal.
6. Process all packs in one work queue. Do not process one pack after the other.
7. Do not copy the entries into tree index order two times.
   - Part 2 added `TreeEntriesBuilder` (`src/models/container.rs`). It records entries in the order pass 2 reads them. Then `finish` copies all three arrays into tree index order.
   - This copy is one more pass over every entry. It also needs a temporary second copy of the largest array (`child`, 4 bytes for each entry): about 0.6 GB for git-ms and about 2.1 GB for linux.
   - The merge in item 5 copies the worker arrays again. Do the reorder one time only. Select one of these:
     - Each worker returns its arrays in read order with its spans. The merge puts the entries into tree index order and changes the name ids in the same pass.
     - Keep the entries in read order. Store a (first position, count) pair for each tree instead of `start[t]..start[t + 1]`. This uses 12 to 16 bytes for each tree instead of 8 (about 100 MB for linux), and needs no reorder.
   - Measure the time of `finish` or the merge, and the peak heap at the end of pass 2, before and after. git-ms after part 2: 3.27 GB peak heap.

How it was done:

- 5A (`7074a8e`): `family_roots` and `work_units`. On linux they take 47 ms and 178 ms.
- 5B (`5a511c2`), still on one thread: one `PackReader` for each unit. `request_times` and the reader keep maps with only the positions of the unit (item 3). The tags are records (item 2). The caches of the units are small, so linux has 0 misses at the 1 GiB limit (233,830 before): 106.2 s to 88.8 s.
- 5C (`22ad553`): the worker results and the merge (items 4, 5, and 7, first option). `NameStore::merge` gives a `NameMap` for each worker. `TreeEntries::merge` replaces `finish`: it puts the entries in tree index order and maps the names in the same pass. One `Parsed` for each worker, not for each unit: with one for each unit, the linux pass 2 peak was 12.2 GB, not 8.8 GB.
- 5D (`d21af25`): one `rayon` queue for the units of all packs and the loose objects (item 6). Each pool thread fills its own `Parsed`. Each reader gets `limit / threads` of the delta cache. `unit_reads` aims for 8 units for each thread, at most 4,096 reads. `TreeEntries::merge` copies each array in parallel.
- Changes to the plan:
  - Item 3: the delta cache and the decoder belong to the `PackReader` of a unit, not to the worker. A worker makes a new reader for each unit. A new decoder costs about 0.4 µs more than a reset one, which is about 0.65 ms for the 1,735 units of linux.
  - Item 5: the workers are merged in thread order. The name ids can be different between runs, because they depend on which worker found a name first. The tree entries are equal for each run and each number of threads.
  - The binary sets the thread count: `max(n / 4, min(n - 1, 8))` of the `n` hardware threads (`parser::default_threads`), unless `RAYON_NUM_THREADS` is set. On 128 hardware threads, pass 2 is not faster with more than about 32 threads, and each thread adds about 15 MB to the peak heap (vscode: 0.69 GB on 1 thread, 1.31 GB on 32, 2.58 GB on 128).
  - The binary sets the `mimalloc` purge delay to 0 (`src/main.rs`). With the default (1 s, 10 s in arenas), linux on 32 threads had a pass 2 peak of 11.2–12.1 GB. With 0, it has 8.1–8.4 GB. Release of the worker arrays on their own threads (`rayon::broadcast`) did not help.

| linux | 18.06 s ± 0.12 s (3 runs) | 17.47–18.43 s, mean 18.11 s | 1.00 | 72% of 25.0 s |

Decision:

- Pass 1 is not much slower than git. On linux it is as fast as git, which also reads the headers on one thread. Thus the costs of pass 1 are not waste that a small change can remove.
- Pass 1 is a large part of the total time (72% on linux). To make it faster, it must use more than one thread, so that it is faster than git.
- Items 1 to 3 below do not do this, and are not necessary:
  - Item 1 decreases memory only. The pass 1 peak heap of linux is 2.69 GB, and the peak of the parse is 9.18 GB in pass 2. Thus item 1 changes no goal.
  - Item 2 uses a profile from before step 4.1. Do not change these costs before a new profile shows them.
  - Item 3 cannot make linux faster: linux has one pack of 5.2 GB. git-ms has three packs (122 MB, 122 MB, and 268 MB), so item 3 can save at most about half of its 1.4 s.
- Do item 4 instead. Start with a new profile of pass 1 on linux, and show it to the user. Then write a design for item 4 and get the approval of the user before you change code.

The costs in the linux profile from before step 4.1:

1. `scan_pack` collects all entries of a pack in a `Vec<ScannedEntry>` before it records them. For the linux pack this is about 600 MB for a short time. Give each entry to `Scan::record` as it is read. Keep the `DeltaGraph` of part 3a: `scan_pack` makes `offsets` for all entries before it reads the headers, so the graph does not need the buffer. (Not necessary, see "Decision".)
2. `HashIndex::insert` (5.1 s) and the sort of offsets (3.0 s). Change these only if a measurement after parts 1 to 5 shows that pass 1 is a large part of the total time. (Not before a new profile, see "Decision".)
3. Packs are independent. A parallel header scan for each pack is possible. Record the results in pack order so that `container.copies` keeps its order. This needs a buffer for each pack, so it conflicts with item 1. Measure before you choose. (Not necessary, see "Decision".)
4. A parallel header scan inside one pack. The pack index gives the offset of each entry, so each thread can read the headers of its own part of the pack. Record the results in offset order, so that `container.copies` keeps its order. The type of a delta entry comes from its base, which can be in a different part. Fill in these types after all parts are read, from the `DeltaGraph`. The size of a delta comes from the first bytes of the delta itself, so each thread can read it.

## Tests

Write the tests first. Make sure that they fail before you change the code.

Unit tests (in the source files):

- `NameStore` (done in part 1): equal bytes give the same id. `get` gives the original bytes. Non-UTF-8 bytes work. `total_bytes` counts each distinct name one time.
- Merge of name stores: two stores with some names in common merge into one store. The id table maps equal names to one merged id.
- `TreeEntries` (done in part 2): entries for each tree come back in their original order. A submodule entry has `u32::MAX`.
- Delta graph and delta cache: see "3a. Tests" and "3b. Tests".
- Decompression (done in part 4): an object inflates to its expected size with one allocation. A stream that is too short or too long gives an error.

Integration tests (in `tests/`, with `Repo` fixtures):

- All existing tests continue to pass.
- A test with a delta cache limit of 1 byte gives the same result as a test with the default limit (part 3b). This proves that cache misses do not change the result.
- A test with 1 thread and a test with 8 threads give the same containers and the same tree entries.
- For each tree, the entries (child hash, name, mode) equal `git ls-tree <tree>` (done in part 2: `tree_entries_match_git_ls_tree`).

Benchmarks (record with `scripts/benchmarks/bench.py run`, compare with `bench.py compare`):

- `pack/decompress_data/*`: 1 allocation (the output) and 0 reallocations for each call (met in part 4).
- `pack/delta_result_size_1000`: 0 allocations. Keep this.
- `content/parse_tree_*`: no allocation for each entry name that is already in the store. Update the benchmarks when the tree parse function changes.
- Add a benchmark for the name store: `intern` of names that are already in the store (the common case), `intern` of new names, and `get`.
- Add a benchmark for a delta-cache hit. It must not allocate or copy the cached bytes.
- `parse_objects_repo` on zed (`GDP_BENCH_REPO`): lower peak live bytes than 549.1 MB and fewer allocations than 5.2 million. Met after part 2: 196.3 MB and 1.10 million. On zed `504a7f2` (the runs of 2026-11-03): baseline 1.124 GB and 10.95 million, after 3b 214.4 MB and 1.20 million.
- Save one run in `docs/benchmarks/` after each part that can change performance, and keep all of these runs. Compare each run with the run before it (the effect of one part) and with the first baseline (the effect of all parts). Delete runs that you made only to examine noise.

Limits of the benchmarks:

- divan counts allocations for each thread (`thread_local!` in divan `src/alloc.rs`). It counts only the thread that runs the benchmark.
- After part 5, pass 2 allocates on worker threads. `parse_objects_repo` then reports too few allocations and too little peak memory. After part 5, use the harness (peak heap) for the memory of `parse_objects`, not `parse_objects_repo`. Add a comment about this to the `parse_objects_repo` benchmark.
- The benchmarks count requested bytes. They do not include allocator overhead or fragmentation. The harness does.
