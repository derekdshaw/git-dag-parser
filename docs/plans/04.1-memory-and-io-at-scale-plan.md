# Step 4.1: Memory and I/O at scale

## Summary

This step makes the parser work on very large repositories.

The parser reads a repository in two passes. Before step 4.1, pass 2 used too much memory on large repositories:

- The parser kept each tree entry as a 64-byte struct, plus a heap allocation for its name. With the maps and edge lists around them, this cost about 140 bytes for each tree entry.
- The linux repository has about 528 million tree entries. The parser passed 48 GB of heap during pass 2 and did not complete.
- git-ms has about 147 million tree entries. The heap grew from 0.3 GB after pass 1 to 17.6 GB after pass 2.

Parts 1 and 2 (name store and flat tree entries) are done. After part 2, linux completes with a 15.88 GB peak heap and git-ms peaks at 3.27 GB. See "Current measurements".

Pass 2 also does unnecessary work. Parts 3 to 5 fix this:

- The delta cache keeps each resolved object and never removes one (1.8 GB for one pack of git-ms).
- Each cache hit copies the cached bytes.
- Each object gets a new zlib decoder, and its output buffer grows from zero.
- Pass 2 uses one thread on a machine with 128 cores.

After this step:

- Tree entries are in compact arrays of about 9 bytes for each entry (done in part 2).
- A name store keeps each distinct entry name one time. Each entry refers to its name by a 4-byte id (done in part 1).
- The delta cache has a size limit and returns references, not copies.
- Pass 2 reuses its decoders, allocates each output one time, and uses many threads.

Step 5 cannot run on large repositories without this step. Step 5 keeps all tree entries in memory for its calculation.

## Current state of the code

### How `parse_objects` works

`parse_objects(git_dir)` in `src/parser/mod.rs` does this:

1. **Pass 1** (`src/parser/scan.rs`, `scan_repository`):
   - It reads the pack indexes and the loose object names.
   - It reads each pack's object headers in pack-offset order (`scan_pack` in `src/parser/pack.rs`). It inflates only the first bytes of each delta, to get its result size. One reused `flate2::Decompress` reads all deltas of a pack.
   - It records every copy of every object in `container.copies` and selects a primary copy for each object.
   - `Scan::finish` sorts each object kind by hash. An object's index is its position in hash order.
   - `scan_pack` collects all entries of a pack in a `Vec<ScannedEntry>` before `Scan::record` gets them.
2. **Pass 2** (`src/parser/bodies.rs`, `read_bodies`):
   - It reads commits, trees, and tags from their primary copies, in pack-offset order. It never inflates blobs.
   - `PackReader::read` (`src/parser/pack.rs`) inflates each object. `decompress_data` makes a new `ZlibDecoder` for each object and reads with `read_to_end` into an empty `Vec`.
   - `resolve_object_at_offset` stores every resolved object in a `DeltaArena` and a `HashMap<u64, DeltaCacheEntry>`, and never removes one. A cache hit copies the bytes out (`to_vec()`). There is one cache for each pack, and it is dropped when the reader moves to the next pack.
   - It parses each commit body into `commits_raw: HashMap<ObjectHash, CommitRaw>`.
   - `parse_tree` (`src/parser/content.rs`) interns each entry name in one `NameStore`, resolves each entry hash to a child index through the `HashIndex`, and records the entry in a `TreeEntriesBuilder`. It does not keep the entry hash.
   - It writes the name and target hash of each tag into `container.tags[i]`.
   - `TreeEntriesBuilder::finish` copies the entries into tree index order. `read_bodies` returns `Bodies { commits_raw, tree_entries, names }`.
3. **After pass 2**: `resolve_commits`, `resolve_tags`, and the ref reader resolve hashes to indices.

`parse_objects` returns the tuple `ParsedObjects = (commits_raw, tree_entries, names, hash_index, container)`.

`init` (`src/commands/init.rs`) runs only `parse_objects` and prints the summary. Part 2 removed `build_relationships` (`src/parser/relationships.rs`, the "Phase 2" of `init`). Step 5 adds its replacement.

### Data structures

- `src/models/name_store.rs`:
  - `NameStore` holds an `intaglio::bytes::SymbolTable<ahash::RandomState>` and a running byte total. Methods: `intern`, `get`, `len`, `total_bytes`.
  - `NameId` is a `u32` newtype (4 bytes). `intaglio::Symbol` is not used outside this file.
- `src/models/container.rs`:
  - `TreeEntries` has four arrays: `start: Vec<u64>` (one item for each tree, plus a last item that is the entry count), `child: Vec<u32>`, `name: Vec<NameId>`, and `mode: Vec<u8>`. This is about 9 bytes for each entry. `TreeEntries::NO_CHILD` (`u32::MAX`) is the child of a submodule or of a child that is not in the store. Methods: `len`, `entry_count`, `entries(tree)`.
  - `TreeEntriesBuilder` records the entries in the order pass 2 reads them, with a `(first position, count)` span for each tree (`Vec<(u64, u32)>`). `finish` copies each array into tree index order, one array at a time.
  - `FileKind` is `repr(u8)`, one byte.
  - `CommitRaw { index, root_tree_hash, parent_hashes, commit_time }`.
  - `HashIndex` is one `HashMap<ObjectHash, ObjectId>`.
  - `ObjectContainer` has `commits`, `trees`, `blobs`, `tags`, `refs`, `packs`, `copies` (`ObjectCopy`, 32 bytes), and `loose_mtimes`. It does not hold a `NameId`.
- `src/models/objects.rs`:
  - `Commit` is 96 bytes. `Tree` and `Blob` are 48 bytes each (`index`, `hash`, `size`, `size_disk`).
  - Object indices are `usize`. Only `TreeEntries.child` uses `u32`.

## Words used in this plan

- **Name store**: a string interner for byte strings (names). It keeps each distinct name one time and gives it a small id. You use the id to get a `&[u8]` reference to the bytes.
- **Interning**: if a name is already in the store, return the id that exists. Do not add the name again.
- **Flat entry arrays**: all tree entries of all trees in a small number of large arrays. Each tree has a start position and an end position in these arrays.
- **Offset order**: the order of objects in a pack file, from the start to the end.
- **Peak heap**: the largest `RssAnon` value of the process (`/proc/<pid>/status`). It does not include the mapped pack pages.

## Decisions already made

- Use `intaglio::bytes::SymbolTable` (crate `intaglio` 1.15, feature `bytes` only) with the `ahash` hasher as the name store. Put it behind our own `NameStore` type, so that the rest of the code does not use `intaglio` directly. Do not keep a `Vec<u8>` for each entry name.
  - `lasso` and `string-interner` accept only UTF-8 `str`. Git names are bytes, so these crates do not fit.
  - `intaglio` keeps each distinct name in its own allocation. This is not a problem: linux has about 100,000 distinct names, so the store has about 100,000 allocations (before part 2, the parser made one allocation for each of about 528 million entries).
  - Its symbols are `u32`. linux has 98,271 distinct names, which is more than `u16` can hold.
- Use `u32` for object indices in the stored data. linux has 10.4 million objects. The limit of `u32` is about 4.29 billion.
- Remove `Tree.blobs`, `Tree.subtrees`, and `Blob.trees`. The flat entry arrays replace them. Calculate reverse edges only when a later step needs them.
- Name ids are for internal use only. Do not write them to a database. Do not use them as a sort key or a tie-break. Thread order can change them between runs.
- Use `flate2` with the `zlib-rs` backend. Reset and reuse decoders. Give each worker its own decoder. Do not share a decoder between threads.
- Give the delta caches one total byte limit for all workers together. Divide the limit between the workers. Do not give each worker a fixed size: 128 workers with 256 MB each would use 32 GB.
- Measure memory as peak heap (`RssAnon`). Do not use `VmRSS`, which includes the mapped pack pages that the system can release.

### 3. Bounded delta cache

1. Keep the pass 2 read order: pack by pack, in offset order.
2. Replace the delta cache with a cache that has a byte limit:
   - Remove the least recently used entries when the cache is full.
   - Git uses 96 MB (`core.deltaBaseCacheLimit`).
   - Start with a total limit of 1 GB for all workers. Add a command option to change it.
3. In offset order, the base of a delta is usually just before the delta. Thus a small cache gets most bases.
4. Cache only commits, trees, and tags. Blobs are never inflated.
5. On a cache hit, return a reference to the cached bytes (`&[u8]`). Do not copy them. In the git-ms profile, 17% of all `memcpy` time was copies of cached bases.
6. Count cache hits, misses, and evictions. Show them in the summary output.

### 5. Parallel pass 2

1. Divide the commits, trees, and tags of each pack into ranges in offset order. Give each range to a worker. Use `rayon`.
   - Loose objects are not in a pack. Put their copies in ranges of their own. A worker reads a loose object with `read_loose_object`.
2. Let the workers borrow the shared data. Do not use `Arc`, `thread::spawn`, or a channel.
   - `rayon` returns only after all workers are done. Thus the workers can borrow values from `read_bodies`. The values do not have to be `'static`. (`build_relationships` used `Arc` only because `thread::spawn` needs `'static` values.)
   - The workers borrow these values and only read them:
     - the open packs (`&[OpenPack]`: the mapped pack bytes and the pack index),
     - the pass 1 result (`&Scan`: `container.copies`, `container.hash_of`, and `primary`),
     - the hash index (part 2 resolves each entry hash to a child index during the parse),
     - `objects_dir`, for loose objects.
   - All these types are `Sync`. Each worker makes its own `PackReader` from `&OpenPack`. `PackReader::new` borrows the pack bytes and the index. It does not copy them.
   - No worker changes `scan.container` during pass 2. Today pass 2 writes the name and target of each tag into `container.tags[i]`. Instead, each worker returns its tags as records. Write them into the container after all workers are done.
3. Each worker owns its delta cache (a part of the total limit), its decoder, and its `NameStore`. Workers do not share a name store and do not use locks for names.
4. Each worker returns its trees as local flat arrays (with local name ids), its commits as raw records, and its tags as records.
5. Merge the results in tree index order:
   - Merge the worker name stores into one store. For each worker, make a table from its local ids to the merged ids. The stores are small (about 100,000 names for linux), so the merge is fast.
   - Change each local name id in the worker's entry arrays to the merged id.
   - The merged result must be the same for any number of threads. Merge the workers in a fixed order (their range order). Name ids are for internal use only, but the entries must be equal.
6. Process all packs in one work queue. Do not process one pack after the other.
7. Do not copy the entries into tree index order two times.
   - Part 2 added `TreeEntriesBuilder` (`src/models/container.rs`). It records entries in the order pass 2 reads them. Then `finish` copies all three arrays into tree index order.
   - This copy is one more pass over every entry. It also needs a temporary second copy of the largest array (`child`, 4 bytes for each entry): about 0.6 GB for git-ms and about 2.1 GB for linux.
   - The merge in item 5 copies the worker arrays again. Do the reorder one time only. Select one of these:
     - Each worker returns its arrays in read order with its spans. The merge puts the entries into tree index order and changes the name ids in the same pass.
     - Keep the entries in read order. Store a (first position, count) pair for each tree instead of `start[t]..start[t + 1]`. This uses 12 to 16 bytes for each tree instead of 8 (about 100 MB for linux), and needs no reorder.
   - Measure the time of `finish` or the merge, and the peak heap at the end of pass 2, before and after. git-ms after part 2: 3.27 GB peak heap.

## Tests

Write the tests first. Make sure that they fail before you change the code.

Unit tests (in the source files):

- `NameStore` (done in part 1): equal bytes give the same id. `get` gives the original bytes. Non-UTF-8 bytes work. `total_bytes` counts each distinct name one time.
- Merge of name stores: two stores with some names in common merge into one store. The id table maps equal names to one merged id.
- `TreeEntries` (done in part 2): entries for each tree come back in their original order. A submodule entry has `u32::MAX`.
- Delta cache: when the cache is over its limit, it removes the least recently used entry. The total bytes stay at or below the limit.
- Decompression: an object inflates to its expected size with one allocation. A stream that is too short or too long gives an error.

Integration tests (in `tests/`, with `Repo` fixtures):

- All existing tests continue to pass.
- A test with a delta cache limit of 1 byte gives the same result as a test with the default limit. This proves that cache misses do not change the result.
- A test with 1 thread and a test with 8 threads give the same containers and the same tree entries.
- For each tree, the entries (child hash, name, mode) equal `git ls-tree <tree>` (done in part 2: `tree_entries_match_git_ls_tree`).

Benchmarks (record with `scripts/benchmarks/bench.py run`, compare with `bench.py compare`):
